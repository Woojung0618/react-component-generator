# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 예외를 두고 싶은 순간이 바로 이 규칙이 가장 필요한 순간이다.

## 0. 우선순위 조항

이 파일은 **기본값(fallback)** 이다. 프로젝트 루트 또는 하위 디렉토리의 `CLAUDE.md`/`AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그 규칙이 이 파일보다 우선**한다. 충돌이 없는 부분은 이 파일을 계속 적용한다.

## 1. 적용 기준

### TDD 반드시 적용

- **비즈니스 로직** (계산, 상태 전이, 조건 분기)
- **API 엔드포인트 / 서버 핸들러**
- **유틸리티 / 순수 함수**
- **버그 수정** (재현 테스트 없이는 수정 착수 금지)

### TDD 불필요

- **타입 정의** (interface, type alias)
- **설정 파일** (eslint, tsconfig, vite config 등)
- **순수 UI** (마크업/스타일만 있고 로직이 없는 프레젠테이션 컴포넌트)
- **SQL / 마이그레이션 스크립트**

애매한 경우: 조건 분기나 로직이 하나라도 섞이면 "적용" 쪽으로 판단한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 몰아넣지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 넘어가는 것은 RED가 아니다.
- 실패 이유는 **오직 "기능 미구현"** 이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 RED로 인정하지 않는다 — 고치고 다시 실행해서 올바른 이유로 실패하는지 확인한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 이 테스트가 요구하지 않는 기능, 파라미터, 분기는 추가하지 않는다.
- **신규 테스트 + 기존 테스트 전체**가 통과하는지 확인한다. 신규 테스트만 통과하고 끝내지 않는다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 수행한다.
- 전 과정에서 **테스트는 계속 green**이어야 한다. 한 번이라도 깨지면 즉시 되돌린다.
- **새로운 동작을 추가하지 않는다.** 리팩토링 중 "이왕 하는 김에" 기능을 얹는 것은 금지 — 그건 다음 RED의 몫이다.

### 반복

다음 동작이 있다면 **RED로 돌아간다.** GREEN이나 REFACTOR 상태에서 바로 다음 기능 코드를 이어 쓰지 않는다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성한 사실을 발견하면, **해당 프로덕션 코드를 삭제**하고 RED부터 다시 시작한다.
- "이미 짰으니 참고용으로 남겨두자"는 **금지**한다. 주석 처리, 별도 파일 보관, `_old` 접미사 등 어떤 형태로도 남기지 않는다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | **단순한 코드일수록 테스트 작성 비용도 낮다.** 단순함은 생략의 이유가 아니라 작성이 쉬운 이유다. 단순한 코드도 요구사항이 바뀌면 깨진다. |
| "나중에 추가하겠다" | **나중은 오지 않는다.** RED 없이 작성된 코드는 검증되지 않은 채 다음 기능 위에 쌓인다. 지금 아니면 영원히 안 한다. |
| "시간이 없다" | **테스트 없이 짠 코드는 디버깅 시간으로 그 값을 반드시 되갚는다.** TDD는 속도를 늦추는 게 아니라 재작업을 없애 총 시간을 줄인다. |
| "삭제하면 낭비" | **검증되지 않은 코드는 자산이 아니라 부채다.** 이미 짠 코드를 지키려다 규율이 무너지는 것이 진짜 낭비다. |
| "프로토타입이다" | **프로토타입은 조용히 프로덕션이 된다.** 지금 예외를 두면 그 예외가 영구 코드베이스의 기준이 된다. |

## 5. 요약

**RED 없이 GREEN 없다. GREEN 없이 REFACTOR 없다. 예외는 없다.**
